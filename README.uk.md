# SPBT_DB

[English](README.md)

SPBT_DB — це вбудована база даних для програм одного типу: бота на Node.js або невеликого сервісу,
що працює одним процесом на маленькому VPS і переріс свої JSON-файли. Вона працює всередині вашого
процесу, зберігає дані у файлах LMDB через [lmdb-js](https://github.com/kriszyp/lmdb-js) і додає
лише те, що потрібно такій програмі: типізовані ключі, індекси, термін дії записів, планувальник,
який переживає перезапуски, і буферизований запис для лічильників, що змінюються на кожне
повідомлення. Її написали для Discord-бота TANO, сервер якого має 1 ГБ оперативної пам'яті.

## Чим вона не є

Усього цього тут немає навмисно. Кожна можливість коштує коду, пам'яті та зусиль на
експлуатацію, а програмі, для якої призначена SPBT_DB, вони не потрібні.

* **Не сервер.** Ні порту, ні демона, ні рядка підключення. Це бібліотека, яка живе у вашому
  процесі.
* **Немає мови запитів.** Ні SQL, ні join'ів, ні агрегацій, ні довільних фільтрів. Ви читаєте за
  ключем і за індексами, оголошеними в схемі.
* **Немає адмін-інтерфейсу чи оболонки.** Дані ви переглядаєте зі свого коду; `db.stats()` показує
  розміри та кількість сторінок.
* **Немає інструмента міграцій.** Записи несуть id схеми, а ваші функції `migrate` оновлюють старі
  записи під час читання. Команди масової міграції немає.
* **Один записувач за раз.** LMDB серіалізує записи. Кілька процесів на одній машині можуть
  ділити файли; кілька машин — ні.
* **Немає реплікації й відновлення на момент часу.** `compactCopy` записує узгоджену копію живої
  бази; куди ця копія піде, вирішуєте ви.
* **Немає браузера, edge чи serverless.** Потрібен нативний модуль lmdb.

Якщо вам потрібне будь-що з цього, беріть SQLite (`node:sqlite`, `better-sqlite3`) або Postgres.
Якщо ваші дані — кілька кілобайт, що рідко змінюються, простіше й достатньо швидко буде JSON-файл,
записаний у тимчасовий файл і перейменований на місце.

Те, що лишилося, невелике:

* близько 3 700 рядків JavaScript (без коментарів), дві залежності (`lmdb`, `msgpackr`) і пакет на
  93 КБ;
* малі записи: XP одного учасника займає на диску 43 Б разом зі сторінками B+tree;
* записи читаються з відображеного в пам'ять файлу на вимогу, а не завантажуються в купу JS, і
  ядро може скинути ці сторінки під тиском пам'яті. Від 10k до 100k користувачів анонімна пам'ять
  ботоподібного процесу трималася на 49–53 МБ, тоді як у JSON-версії зросла з 23–24 МБ до
  82–84 МБ.

Фіксовані витрати: завантаження нативного модуля lmdb додає близько 18 МБ RSS, а його готова
збірка — це 15 МБ із 20 МБ після встановлення.

## Цифри

Виміряно на ноутбуці з AMD Ryzen 5 7535HS (Zen 3+), Linux 7.1, btrfs (zstd) на NVMe, Node
22.23.1, з теплим page cache. Порівняння — з кодом сховища TANO v26, запущеним без змін
(`bench/v26-stores.mjs`). Повні таблиці: [`bench/results-2026-10-14-json-vs-spbtdb.md`](bench/results-2026-10-14-json-vs-spbtdb.md).

Читання, які v26 виконувала розбором цілого файлу, стали в 35–55 000 разів швидшими, і розрив
росте разом з даними. Гарячий шлях на кожне повідомлення — приблизно в 5 разів швидший, читання
конфігів — у 2 рази. Поодинокі довговічні записи повільніші за небезпечне переписування файлів у
v26, поки файли малі, а процес споживає на 20–35 МБ більше RAM, доки даних не побільшає. Нічого з
цього ще не вимірювали на продакшн-сервері.

## Швидкий старт

SPBT_DB ще немає в реєстрі npm. Встановіть її з GitHub:

```sh
npm install github:DanyloKob/SPBT_DB    # Node 22 or newer
```

```js
import { open } from 'spbt-db';

const db = open({ dir: './data' });            // creates data/hot.mdb; { backend: 'memory' } for tests

// the core collections are opened for you: guild, guild_feature, feature_config, user, news, level, kv
db.level.put({ gid: '1100000000000000001', uid: '300000000000000001', xp: 120 }); // ids: string, bigint or number
db.level.get('1100000000000000001', '300000000000000001');      // -> { xp: 120 }
db.level.top('1100000000000000001', 10);                         // -> [{ gid, uid, xp }], from an index

// your own collection, with an index
const tickets = db.collection('ticket', {
  key: 'gid:u64 no:u32',
  indexes: { ticket_by_user: { key: 'gid:u64 uid:u64 no:u32' } },
});
db.txn(() => {                                  // atomic; committed when it returns
  tickets.put({ gid: 1n, no: 7, uid: 42n, subject: 'refund' });
  db.kv.put({ k: 'ticket_counter:1', n: 7 });
});
tickets.query({ index: 'ticket_by_user', where: [1n, 42n] }).items;

await db.close();                               // flushes buffers, marks the shutdown clean
```

У `examples/` — три програми, які можна запустити: XP і лідерборд (`xp-leaderboard.mjs`),
тимчасові бани через планувальник (`tempban-scheduler.mjs`) і сесії з TTL (`ttl-sessions.mjs`).

## Поняття

**Середовища.** Дані живуть щонайбільше у двох файлах LMDB: `hot.mdb` (сторінки по 4 КіБ) для
малих записів, які читаються на кожну подію, і `cold.mdb` (сторінки по 8 КіБ, відкривається при
першому використанні) для журналів. Транзакція ніколи не охоплює обидва.

**Колекції та ключі.** Колекція — це схема з ключем: `'gid:u64 uid:u64'`. Ключі кодуються в
big-endian і фіксованої ширини, тож порядок байтів збігається з логічним, і кожен запит за
діапазоном — це діапазон B+tree. Типи: `u8 u16 u24 u32 u48 u64 u64s inv32 inv48 str bN`. `u64`
приймає Discord-id як bigint, десятковий рядок або безпечне ціле число і декодується в bigint
(`u64s` — у рядок). `inv32`/`inv48` зберігають `max - n`, що дає спадний порядок (його використовує
лідерборд).

**Записи.** Збережене значення ніколи не повторює ключ. Це маленький заголовок (необов'язковий id
схеми, час оновлення, термін дії) і payload в одному з трьох кодеків: msgpack зі структурами,
спільними для колекції, varint (`level` зберігає XP у 2–6 байтах) або сирі байти. msgpack-payload
від 512 Б стискається deflate, якщо це його зменшує. `schemaId` і `migrate` оновлюють старі записи
під час читання.

**Індекси.** Оголошуються в схемі й записуються в тій самій транзакції, що й запис. Підтримуються
`unique`, `filter` (розріджений індекс) і `covered`-запити (відповідь з самого індексу). Індекс з
`lag: n` записує свої елементи раз на `n` рядків, а не в кожній транзакції, — для даних, що лише
дописуються, з ключем, упорядкованим за часом; читання підмішують ще не записаний хвіст з RAM.

**Транзакції.** `db.txn(fn)` синхронна й атомарна, вкладений виклик — це savepoint.
`db.txnAsync(fn)` виконує коміт і fsync поза головним потоком. LMDB має одного записувача за раз,
тож read-modify-write (`incr`, `patch`) атомарний навіть між процесами.

**TTL.** Термін дії — частина запису: читання після нього одразу повертає `undefined`. Прибирач
лише звільняє місце — обмеженим щоденним скануванням (за замовчуванням) або однією задачею
планувальника на запис.

**Планувальник.** `db.sched.at(when, { kind, gid, subject, payload })` записує рядок задачі з
ключем за часом виконання; у вашій транзакції бан і його зняття комітяться разом. Один таймер на
процес, ніколи не довший за 60 с. Доставка — щонайменше один раз, з повторами й backoff, трьома
політиками наздоганяння для задач, чий час настав, поки процес не працював, і скасуванням за
`(gid, kind, subject)` через індекс.

**Коалесери.** Гарячі записи буферизуються в RAM і комітяться однією транзакцією: `db.level.bump()`
додає XP приблизно за 0,2 мкс, а буфер записується кожні 30 с або на 2 000 учасників. kill -9
втрачає щонайбільше це вікно, і наступний старт про це знає (`db.bootInfo().lastShutdownClean`).
Елемент, який неможливо записати, відкидається окремо, а не блокує всю пачку.

**Часові бакети.** `db.bucketed('event_log', schema, { retentionDays: 30 })` зберігає кожен місяць
UTC в окремій колекції. Запити зливають місяці; ретеншн видаляє цілі місяці однією транзакцією.

**Вектори та блоби** (необов'язково). `attachVectors(db)` з `spbt-db/vector` додає вектори int8 для
кожної гільдії; вони скануються точно маленьким ядром на WebAssembly SIMD: k-NN по 5 000 векторів
тут займає близько 0,1–0,2 мс. `attachBlobs(db, { dir })` з `spbt-db/blobs` зберігає файли за
хешем вмісту з лічильниками посилань у базі, тримає блоби до 1 КБ прямо в базі й прибирає
непотрібні після пільгового періоду.

**Бекенди.** Усе вищеописане звертається до інтерфейсу `Backend` із семи методів. `lmdb` —
справжній; `memory` — для тестів. `test/backend-conformance.test.js` перевіряє обидва на тому
самому контракті.

Дизайн, відхилення від нього й усі раунди вимірювань — у
[`docs/engineering-notes.md`](docs/engineering-notes.md).

## Гарантії

* **Атомарні транзакції.** `db.txn()` або комітиться повністю, або нічого по собі не лишає. Коли
  вона повертається, коміт бачать усі читачі — і в цьому процесі, і в інших.
* **Падіння процесу не пошкоджує базу.** У crash-тесті цього репозиторію записувача вбивали
  SIGKILL по 100 разів у кожному з двох записаних прогонів, поки він комітив транзакції до 200
  користувачів: кожне повторне відкриття вдалося, жоден підтверджений коміт не зник, жодна
  транзакція не застосувалася наполовину, і кожен індекс збігся з даними. Набір тестів з TANO v27
  (`bench/04-crash-safety.mjs`) вбивав записувачів близько 1 500 разів під час приблизно 67 000
  транзакцій з тим самим результатом, і було показано, що його перевірка ловить штучно внесене
  пошкодження.
* **Втрату живлення не тестували.** kill -9 зберігає page cache. Кожен коміт тут коштує близько
  3 мс — це fsync; `await db.flushed()` завершується, коли ОС повідомляє, що всі коміти скинуто на
  диск.
* **Коалесовані записи** довговічні після свого flush. Падіння втрачає щонайбільше `flushMs` таких
  записів (30 с XP, 5 с журналів), і наступне відкриття повідомляє `lastShutdownClean: false`.
* **Кілька процесів** можуть відкрити ті самі файли. Читачі бачать коміт приблизно за 1 мс, а
  записувач, убитий з утриманим блокуванням запису, не блокує наступного.

## Обмеження

* **Ще не виміряно на продакшн-сервері.** Бот працює на Oracle Cloud VM.Standard.E2.1.Micro (AMD
  EPYC 7551, Zen 1, 2 ГГц burstable, 952 МБ RAM, ext4). Усі цифри тут — з ноутбука, у кілька разів
  швидшого на ядро, з іншою файловою системою. Доки бенчмарки там не запущено, прогнози нижче —
  лише припущення.
* **Цілі, які досі не досягнуто**, за останнім повним прогоном набору (`bench/results-2026-10-14-nvme-r2.md`)
  і прогонами розміру сторінки від 2026-10-18 (`bench/results-2026-10-18-cold-pagesize.md`):

  | перевірка | ціль | виміряно тут | прогноз для сервера |
  |---|---|---|---|
  | гарячий `level.get` / `user.get`, p50 | ≤ 2 мкс | 1,25 / 1,40 мкс | ~3,0 / ~3,4 мкс |
  | останні 100 рядків журналу каналу, p99 | ≤ 200 мкс | 346 мкс | ~830 мкс |
  | діапазон лідерборду на 100, p99 | ≤ 200 мкс | 114 мкс | ~275 мкс |
  | сторінки `.mdb`, резидентні під змішаним навантаженням | ≤ 53 МБ | 41 МБ при 0,1 повного обсягу даних; 63–66 МБ при 0,3 | на повному обсязі більше; ядро може скинути ці сторінки, але бюджет сервера їх враховує |
  | відкриття після kill -9, p99 | ≤ 50 мс | 1,69 с у наборі (200 вбивств); 23–27 мс у двох прогонах порівняння з JSON (по 100 вбивств), з одним викидом на 1,6 с | найімовірніше, зупинки writeback у btrfs (див. нотатки); на ext4 не виміряно |

  Прогноз множить на припущені 2,4× для повільнішого CPU; `bench/00-calibrate.mjs
  --save-target` замінить припущення, щойно його запустять на сервері.

  Журнал подій не вклався в проєктну ціль 1,6× для write amplification і тепер має власну. Простий
  потік дописування, як і раніше, мусить лишатися під 1,6× і лише на своїх даних досягає 1,50×.
  Журнал з індексами за каналом і за повідомленням та 80 активними каналами записує 2,4× при 512
  рядках на коміт і 2,9× при 250 — проти нових меж 3,0× і 3,5×. Будь-який розклад, що зберігає
  порядок за каналом, коштує більше. На проєктному піку в 50 повідомлень на секунду це 23–28 КБ/с
  запису (див. інженерні нотатки).

* **Один записувач за раз.** Кожен довговічний коміт чекає на диск, тут близько 3 мс, тож один
  записувач встигає приблизно 300 довговічних комітів на секунду. Групуйте записи в одній
  `db.txn()` (100 оновлень користувачів на транзакцію дали 8 000–22 000 на секунду) або
  використовуйте коалесер.
* **Малі записи не малі.** Copy-on-write B+tree переписує цілі сторінки: одне довговічне оновлення
  одного користувача записує 32–57 КБ (дані, два індекси, список вільних сторінок, meta-сторінка).
  Зі стандартним flush раз на 30 с одне оновлення XP записує від 74 Б до 3,6 КБ залежно від
  кількості учасників — у 3–6 разів більше, ніж записувало 2-хвилинне переписування файлу в v26;
  за однакового 2-хвилинного інтервалу вони приблизно рівні.
* **Більше RAM на малих даних.** З 1 000 користувачів ботоподібний процес використав 86 МБ проти
  64 МБ у v26. Більшість цього — завантаження бібліотеки: голий процес Node займає 53 МБ, а
  імпорт SPBT_DB доводить його до 71 МБ ще до відкриття будь-яких даних. На 100 000 користувачів
  розрив зникає (122–126 проти 129–131 МБ). Частина цифри SPBT_DB — відображені сторінки бази,
  які ядро може скинути під тиском пам'яті; у v26 це вся купа.
* **Значення понад ~2 КБ займають цілі сторінки.** LMDB переносить значення, що не вміщається в
  половину сторінки, в overflow-сторінки, тож новина на 2 КБ займає на диску 4,1 КБ. Тримайте
  гарячі записи малими або розбивайте їх.
* **Поки що лише Linux x64.** lmdb-js має збірки для macOS і Windows, але ці тести там ніхто не
  запускав.
* **0.1.0, один користувач.** Її написали для бота TANO, і вона ще не працювала на продакшн-сервері
  цього бота. Блокування put/gc у сховищі блобів працює лише в межах одного процесу.

## Бенчмарки

```sh
npm run bench:json -- --dir ~/.cache/spbtdb-bench   # v26 JSON files vs SPBT_DB (about 8 minutes)
npm run bench:size                                   # lines of code, package size, RAM, bytes per record
npm run bench:suite -- --dir ~/.cache/spbtdb-bench  # the full suite from TANO v27 (bench/run.mjs)
npm run bench                                        # a quick get/put micro-benchmark (bench/quick.mjs)
```

Вказуйте в `--dir` справжній диск. На tmpfs fsync нічого не коштує, і цифри нічого не означають.

**JSON проти SPBT_DB** (`bench/json-vs-spbtdb.mjs`). Кожне сховище й кожен розмір запускаються в
окремому процесі. Бік v26 — це код v26: кожне читання — `readFileSync` + `JSON.parse` цілого файлу,
кожен запис — `writeFileSync` цілого файлу з відступами, без fsync. Бік SPBT_DB робить те, що
новий бот робить на ту саму подію. Результати: [`bench/results-2026-10-14-json-vs-spbtdb.md`](bench/results-2026-10-14-json-vs-spbtdb.md)
і другий прогін, [`-run2`](bench/results-2026-10-14-json-vs-spbtdb-run2.md), що збігся з першим у
межах 12 % за кожною цифрою пропускної здатності.

## Звідки вона

TANO — Discord-бот з веб-панеллю, що працює одним процесом Node.js на невеликій хмарній VM. До
v26 він тримав усе в JSON-файлах: близько 8–12 синхронних читань файлів на кожне повідомлення і
повне переписування файлу, без rename і без fsync, на кожну зміну. Падіння посеред запису могло
спорожнити файл, і бот тоді стартував без жодних даних з нього. Для v27 сховище перепроєктували
під реальні обмеження сервера (1 ГБ RAM, що вже йде у своп, повільний burstable CPU), і цю базу
написали за тим дизайном. Усередині бота вона називалася TanoDB. SPBT_DB — той самий код,
опублікований окремо після рев'ю, яке виправило 11 помилок коректності (див.
[CHANGELOG.md](CHANGELOG.md)).
